# Vouch

**Verified hiring, by default.**

Vouch stops job-offer and recruiter-impersonation scams by giving every hiring
action a cryptographic paper trail — instead of asking a candidate to "trust
but verify" a PDF or an email, Vouch lets them check it in one click and get
an honest answer: **Verified**, **Scam**, or **Can't Verify** (never a false
accusation).

Built for NYU's *Trust in the Hiring Funnel* hackathon. Every feature
described below is implemented and working end-to-end — this is not a mockup.

---

## The problem

Job-offer and fake-recruiter scams are rampant, and there is currently no way
for a candidate to check whether an offer letter, a recruiter email, or a
DM is actually from the company it claims to be from. Candidates are stuck
Googling "is this offer real" and guessing.

## What Vouch does

Vouch gives companies a way to **cryptographically sign** every offer letter
they issue and **register** their real recruiters and domain, and gives
candidates a free tool to check any of the following in seconds:

| Check | How | Verdicts |
|---|---|---|
| **Offer letter (PDF)** | Re-hashes the uploaded PDF and checks it against the Ed25519 signature stamped on it at issue time | Verified / Scam (tampered) / Can't Verify |
| **Offer ID / QR code** | Looks up the signed record by ID (what scanning the QR on a stamped PDF does) | Verified / Scam / Can't Verify |
| **Sender email** | Parses the sender's domain + `Authentication-Results` (SPF/DKIM/DMARC), checks it against the company's registered domain and recruiter list, and flags look-alike domains | Verified / Scam / Can't Verify |
| **Free-text message** | Scans the text for known scam patterns (upfront payment, gift cards, check-cashing, urgency, off-platform chat requests, etc.) — can never confirm a sender, only flag red flags in the wording | Scam / Can't Verify |

The verdict engine (`backend/verdict.py`) is intentionally conservative: a
company that has never joined Vouch always comes back **Can't Verify**, never
a false **Scam**. "Scam" is reserved for actual hash mismatches, look-alike
domains, or hard-fail scam-language patterns.

### Why this is a real product, not just a hackathon demo

- **Two-sided model**: companies onboard once (verify their domain, register
  recruiters, sign offers through their ATS or by hand); candidates get a
  free, no-signup verification tool. The free tool is the growth loop that
  drives employer signups.
- **Fits into existing hiring infra**: the ATS webhook path
  (`POST /api/ats/webhook`, HMAC-signed like Stripe/GitHub webhooks) means an
  ATS (Greenhouse/Lever/Workday-style) can auto-sign every offer it sends with
  zero manual work from the recruiter.
- **Multiple surfaces**: a web verify page, a QR code on the PDF itself, a
  Chrome extension that checks emails right inside Gmail, and a Slack bot —
  candidates and employees can check trust wherever they already are.

## Quick start

```bash
# 1. Install dependencies
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2. Seed demo data (creates a verified company, a recruiter, and a signed
#    sample offer, so the verify page has real data to check immediately)
python3 seed_demo_data.py

# 3. Run the API + frontend (same server serves both)
uvicorn backend.main:app --reload --port 8000
```

Then open:

- **`http://localhost:8000/app`** — the combined dashboard (candidate verify
  tool + employer onboarding wizard, tabbed, single page)
- **`http://localhost:8000/verify`** — the standalone candidate verify page
  (Offer PDF / Offer ID / Email / Text tabs)
- **`http://localhost:8000/docs`** — interactive Swagger API docs (auto-generated by FastAPI)

To confirm everything works end-to-end without clicking through the UI:

```bash
python3 demo/run_demo.py
```

This runs 14 automated checks against the live server — signing, tampering,
verifying, the webhook path, look-alike domain detection, and text scanning —
and prints pass/fail for each. It currently passes 14/14.

To try the offer-letter check with real files, `test_offers/` has a matched
pair: `genuine_offer_letter.pdf` (verifies as **Verified**) and
`tampered_offer_letter.pdf` (a copy with the salary line edited after
signing — verifies as **Scam**, hash mismatch).

To simulate an ATS auto-signing an offer:

```bash
python3 mock_ats/send_offer.py --job "Software Engineer" --name "Alex Rivera" --email alex.rivera@gmail.com
```

## Architecture

```
Company onboarding                  Candidate verification
───────────────────                 ───────────────────────
create company                      upload offer PDF ──┐
  → DNS TXT ownership proof                             │
  → domain classified (official/                        ├─ re-hash + check
    look-alike/unregistered)                             │  Ed25519 signature
  → Ed25519 keypair generated                            │
register recruiters                 paste offer ID / ────┤
issue signed offer                  scan QR code          │  look up signed
  (manual upload OR                                       │  record by ID
   ATS webhook, HMAC-signed)        paste sender email ───┤
  → PDF stamped with QR +            or raw source          → domain match +
    verify footer, hash                                     SPF/DKIM/DMARC +
    stored                                                  recruiter registry +
run look-alike domain scan                                  look-alike check
  → flags punycode/typo                paste free text ───┤
    domains that resolve                                    → scam-pattern regex
                                                              scan only
                                     ▼
                            verdict engine (backend/verdict.py)
                            Verified · Scam · Can't Verify
```

**Trust primitives used (all real, no "trust me" logic):**

- **Ed25519 signatures** — one keypair per company (`cryptography` library),
  canonical JSON serialization so signing and verifying always agree on the
  bytes that were signed.
- **SHA-256 tamper fingerprinting** — every stamped PDF's content hash is
  stored at signing time; any edit after signing changes the hash and the
  verdict flips to Scam.
- **DNS TXT domain-ownership proof + RDAP domain age + MX/liveness checks** —
  a company can only get "official" domain status by proving they control
  the domain's DNS, and look-alike candidate domains are checked for whether
  they're even registered/live before being flagged.
- **SPF/DKIM/DMARC parsing** from the email's `Authentication-Results`
  header (Vouch reads what the receiving mail server already verified,
  rather than re-implementing mail auth crypto).
- **HMAC-SHA256 webhook signing** (Stripe/GitHub-style) with idempotent
  replay protection for the ATS integration path.
- **Homoglyph + fuzzy-match look-alike detection** (e.g. `rnicrosoft.com`,
  `micros0ft.com`) combined with permutation generation, so a company doesn't
  have to know every possible scam domain in advance.

## API reference

All routes are served by `backend/main.py` (FastAPI). Interactive docs at
`/docs` when the server is running.

### Company onboarding

| Method & path | Purpose |
|---|---|
| `POST /api/company` | Create a company; returns a DNS TXT token to prove domain ownership |
| `GET /api/company` | List all companies (public fields only — no keys/secrets) |
| `POST /api/company/{id}/verify-domain` | Check the DNS TXT record; on success, generates the company's Ed25519 keypair and marks the domain verified |
| `POST /api/company/{id}/dev-force-verify` | **Demo-only** shortcut that skips the DNS check (see Security notes) |
| `GET /api/company/{id}/webhook-secret` | Fetch the company's ATS webhook HMAC secret |
| `GET /api/company/{id}/trust-file` | Public `hiring-trust.json` for the company (domain, public key, registered recruiters) |
| `POST /api/company/{id}/recruiters` | Register a recruiter's name/email |
| `GET /api/company/{id}/recruiters` | List a company's registered recruiters |

### Offers

| Method & path | Purpose |
|---|---|
| `POST /api/offers` | Manual offer upload → stamp the PDF (QR + verify footer) and sign it |
| `GET /api/company/{id}/offers` | List a company's issued offers |
| `POST /api/ats/webhook` | ATS webhook receiver (HMAC-verified) → auto stamp + sign |
| `GET /api/offers/{offer_id}` | Public offer record, looked up by ID (what a QR scan hits) |
| `GET /api/offers/{offer_id}/verify` | JSON verdict for an offer ID |
| `GET /v/{offer_id}` | HTML QR-scan landing page |

### Verification (candidate-facing)

| Method & path | Purpose |
|---|---|
| `POST /api/verify/pdf` | Upload a PDF → re-hash and check its signature → verdict |
| `POST /api/verify/email` | Raw email source, or just a sender address (+ optional body text) → verdict |
| `POST /api/verify/text` | Free-text message → scam-pattern flags only (can't confirm a sender) |
| `GET /verify` | HTML candidate verify page (Offer PDF / Offer ID / Email / Text tabs) |
| `GET /app` | HTML combined dashboard — candidate verify tools *and* the employer onboarding wizard in one page |

### Look-alike domain monitoring

| Method & path | Purpose |
|---|---|
| `POST /api/company/{id}/monitor/scan` | Generate look-alike domain candidates and check which ones are actually registered/live |
| `GET /api/company/{id}/lookalikes` | List domains flagged for a company, with risk level |

## Security notes & known limitations

This was built in one day for a hackathon. Before any real deployment:

- **`dev-force-verify` is a demo-only bypass.** It marks a company's domain
  "verified" without checking the DNS TXT record, so a live demo isn't
  blocked on real DNS propagation. This endpoint must not exist in
  production — real domain verification should always go through
  `verify-domain`.
- **CORS is wide open (`allow_origins=["*"]`)** to make local development and
  the Chrome extension simple to wire up. A production deployment should
  restrict this to known origins.
- **SQLite + per-company keys stored in the same DB file** are fine for a
  hackathon; a production version should move to Postgres and store private
  keys in a proper KMS/secrets manager rather than a database column.
- **The Chrome extension scrapes Gmail's DOM** using unofficial CSS class
  hooks (`span.gD`, `h2.hP`, `div.a3s`), because that's what's accessible
  without shipping OAuth. This is inherently fragile (Gmail can change its
  markup) and can't see raw email headers, so it can't check SPF/DKIM/DMARC
  the way `/api/verify/email` can when given full raw email source. A
  production version should use the official Gmail API (OAuth) instead.
- **Public endpoints never expose secrets.** `GET /api/company` was
  specifically written to return only public fields (name, domain,
  verification status) — company private keys and webhook secrets are only
  ever returned from their own dedicated, purpose-built endpoints.
- **Look-alike detection is permutation + fuzzy-match based**, not a full
  threat-intel feed. It catches common typo-squatting and homoglyph domains
  but isn't exhaustive.
